# Noespire Frontend V1 — Production Spec

Status: FROZEN (including the crash-consistency rulings in §7.2–7.3 and the
freeze rulings in §13), ready for implementation. This spec is the contract
between product decisions (CONTEXT.md, ADR-0001…0005, prototype verdict) and
the first production vertical slice. It introduces **no** changes to proof
semantics; `src/research/` remains untouched in behavior (see §8.4 for the
single instrumentation-adjacent question and its resolution).

Implements: the Home → Create Problem → Workspace → one attempt → RUNNING →
OPEN/SOLVED/ERROR → inspect → manual Retry vertical slice.

---

## 1. Scope

In scope:

- Problem list, problem creation (statement only), open a problem.
- Problem Workspace with `Proof | Attempts` tabs (prototype Variant B), state
  deciding only the default tab (SOLVED→Proof, OPEN/RUNNING→Attempts).
- One background proof attempt per problem at a time; manual Retry;
  Revise & Fork; Archive.
- Inspector overlay drawer for machine metadata.
- Thin application layer: loopback REST API, background execution wrapper,
  problem discovery/index, workspace read model (ADR-0005).

Out of scope (explicit non-goals, §12): Research Graph, multi-obligation
scaffold UI, Lean/kernel verification, WebSocket/SSE, database, auth,
multi-user, dark mode, streaming, cancellation, analytics.

## 2. Frozen Product Decisions (recap, binding)

- Noespire V1 = Research Workspace; Problem = top-level object; Workspace =
  root container.
- Layout = prototype **Variant B** (explicit tabs). Variants A/C rejected.
- Inspector = right overlay drawer; machine metadata never in body text.
- Search state and verified truth are visually separate (ADR-0003).
- Every verified artifact is labeled `LLM-verified`; green is reserved for a
  future kernel-verified state (ADR-0004).
- Revision = fork, never edit (ADR-0001). No Delete anywhere; Archive only.
- Frontend reaches the research core only through the application layer
  (ADR-0005) — never reads `obligations.json`, `attempts/*.json`,
  `facts/*.md` itself.
- RUNNING phase text (`Generating candidate…` / `Checking candidate…`) is a UI
  heuristic derived from attempt-artifact field presence, never claimed as a
  backend phase; elapsed time is session-scoped unless sourced from the
  application-layer execution log (§7).

## 3. Architecture

Three tiers, two seams:

```text
frontend/        React 18 + TypeScript + Vite + KaTeX (loopback web UI)
    │  HTTP/JSON only — depends on the REST contract, nothing else
    ▼
application/     Python + FastAPI (loopback 127.0.0.1)
    │  calls library functions; never shells out, never parses core files
    │  it doesn't own (exception: its own index + execution log)
    ▼
research/        src/research/* — existing core, unchanged
```

Module map (codebase-design language):

- **`research` core** — deep modules already exist: `solve_problem_once`,
  `FactGraph`, `ObligationRegistry`. Interface: Python calls. Knows nothing
  about HTTP or UI.
- **`application`** — owns four modules:
  1. `problem_index` — discovery/listing (§4).
  2. `workspace_read_model` — the single deep read module (§5); the REST
     layer is a thin adapter over it.
  3. `execution` — background wrapper around `solve_problem_once` (§7).
  4. `http` — FastAPI adapter exposing the REST contract (§6); the only
     module that knows HTTP.
- **`frontend`** — consumes the REST contract; all rendering decisions local.

Interface discipline: the frontend↔application seam is the REST contract
(§6); tests cross the same seams — application tests call Python interfaces,
frontend tests mock the REST contract.

## 4. Storage Layout

All state is file-backed under one operator-chosen data root (default
`workspaces/`, configurable at server start). No database.

```text
workspaces/
├── index.json                      # application-owned problem index
└── <problem_id>/
    ├── obligations.json            # research core (ObligationRegistry)
    ├── facts/                      # research core (FactGraph)
    ├── attempts/                   # research core (attempt evidence)
    └── _execution_log.jsonl        # application-owned execution records
```

`index.json` (application-owned; the only listing source):

```json
{
  "problems": [
    {
      "problem_id": "even-perfect-triangular-a1b2c3",
      "statement": "Every even perfect number is triangular.",
      "derived_from": null,
      "archived": false,
      "created_at": "2026-08-31T10:15:00+08:00"
    }
  ]
}
```

Rules:

- `problem_id` is generated by the application layer: slug of the statement
  prefix + 6-char sha256 suffix of (statement + creation time). Users never
  type ids.
- The workspace directory of a problem is `workspaces/<problem_id>/`;
  `FactGraph` root = that dir, registry path = `obligations.json` inside it.
  (These are exactly the constructor arguments the research core already
  takes.)
- `derived_from` and `archived` live only in the index. Archive never touches
  facts/attempts/lineage.
- Research-core files are written only by research-core code. The
  application layer writes `index.json` and `_execution_log.jsonl` only.
- Atomic writes (tmp + replace) for `index.json`, matching core practice.

## 5. Workspace Read Model

`GET /api/problems/{id}` returns this aggregate. It is the only object the
workspace UI needs; the frontend never stitches registry + attempts + graph.

```jsonc
{
  "problem_id": "…",
  "statement": "…",
  "status": "OPEN | RUNNING | SOLVED",     // derivation below
  "derived_from": "… | null",
  "archived": false,
  "obligation": {                           // from obligations.json
    "obligation_id": "root:<problem_id>",
    "goal": "…", "premises": ["…"],
    "route_id": "root",
    "status": "OPEN | RUNNING | DISCHARGED",
    "resolved_by_fact_id": "… | null"
  },
  "attempts": [                             // oldest → newest
    {
      "attempt_id": "attempt-000007",
      "verdict": "RUNNING | PASS | FAIL | ERROR",
      "failure_class": "contract | rejection | runtime | interrupted | null",
      "candidate": { "statement": "…", "proof": "…", "predecessors": ["…"] } | null,
      "verifier":  { "accepted": false, "reason": "…" } | null,
      "error": "… | null",
      "started_at": "… | null",            // from execution log only
      "finished_at": "… | null"
    }
  ],
  "target_fact": { "fact_id": "…", "statement": "…", "proof": "…",
                   "predecessors": ["…"] } | null,     // null unless SOLVED
  "supporting_closure": [                   // topo order; [] unless SOLVED
    { "fact_id": "…", "statement": "…", "proof": "…", "predecessors": ["…"] }
  ],
  "live": { "running": true, "current_attempt_id": "attempt-000007" }
            // present only when status == RUNNING
}
```

Field sources and rules:

| Field | Source | Notes |
|---|---|---|
| `status` | derived | `SOLVED` iff obligation `DISCHARGED`; else `RUNNING` iff a live task exists for the problem (in-memory task table is authoritative, **not** a stale attempt file); else `OPEN` |
| `attempts[*]` | `attempts/attempt-*.json` | read verbatim |
| `failure_class` | execution log + verdict | see §8; `null` for PASS/RUNNING |
| `started_at/finished_at` | `_execution_log.jsonl` | `null` if absent (pre-V1 evidence) |
| `target_fact` / `supporting_closure` | `FactGraph.get_fact` / `supporting_closure` | only when DISCHARGED |
| `live` | in-memory task table | absent otherwise |

Error semantics: unknown problem_id → 404. Corrupt/missing core files →
500 with a plain error body; the read model never guesses. A RUNNING-verdict
attempt with no live task is reported with `failure_class: "interrupted"`
(see §7.3).

Nullable semantics: anything sourced from a file that may legitimately not
exist yet is `null`/empty — never omitted, so the frontend renders explicit
empty states.

## 6. REST Contract

Loopback only (`127.0.0.1`, port configurable, default e.g. 8173). JSON in
and out. Six endpoints — Retry is deliberately *not* its own verb (it is
"start an attempt" again).

### `GET /api/problems`

→ 200: `{ "problems": [ { problem_id, statement, status, archived,
derived_from, attempt_count, last_activity } ] }` sorted by last activity
desc. `last_activity` = latest execution-log or attempt-file mtime; `null`
if none. Archived problems included; the frontend filters by default.

### `POST /api/problems`

Body: `{ "statement": string }`. → 201 with the created entry
(`{ problem_id, statement, status, derived_from, archived }`). **400** if the
statement is blank or whitespace-only (amended from 422 at Slice 2 freeze);
genuine internal errors are never masked as 400. Creates the workspace dir
and index entry; **no** obligation is created yet (the core creates it on
first solve — a problem that was never attempted legitimately has no
registry content; read model reports `status: OPEN`, `attempts: []`,
`obligation: null`).

### `GET /api/problems/{problem_id}`

→ 200 WorkspaceReadModel (§5). 404 unknown id. This is the polling endpoint;
it must stay cheap (small JSON files; no LLM involvement).

### `POST /api/problems/{problem_id}/attempts`

Starts one background attempt. → 202 `{ "status": "accepted" }` (amended at
Slice 3: the body is a bare acceptance ack; only the HTTP status drives
client behavior).
409 `{ "error": "already_running" }` if a live task exists for the problem.
409 `{ "error": "already_solved" }` if the problem is SOLVED (obligation
DISCHARGED): 202 means "accepted for execution", and a discharged obligation
executes no worker/verifier, so the API refuses explicitly instead of
silently no-oping through the core's DISCHARGED short-circuit.
404 unknown id. The response carries no attempt id (ruled at freeze): the
attempt file only exists once execution starts, `_start_attempt` sequencing
in `problem.py` stays untouched, and at one-execution-per-problem the UI
learns the id by polling the read model. The application layer may use an
internal `execution_id` for log correlation (§7.2) without exposing it.

Failure cases that matter: two rapid Retry clicks → second gets 409 (the UI
also disables Retry while RUNNING; the 409 is the authority). Fork of an
archived problem is allowed (archived ≠ frozen).

### `POST /api/problems/{problem_id}/fork`

Body: `{ "statement": string }`. → 201 `{ "problem_id" }` of the new
problem with `derived_from` set. 404 unknown parent / 400 invalid
statement. The old problem is untouched (ADR-0001).

### `POST /api/problems/{problem_id}/archive`

Body: `{ "archived": boolean }`. → 200. Idempotent. 404 unknown id.

Failure cases that matter: two rapid Retry clicks → second gets 409 (the UI
also disables Retry while RUNNING; the 409 is the authority). Fork of an
archived problem is allowed (archived ≠ frozen).

## 7. Background Execution Semantics

### 7.1 Model

`POST …/attempts` enqueues an in-process `threading.Thread` (one per problem
at a time, guarded by an in-memory `{problem_id: task}` table) that calls
`solve_problem_once(...)` with the real `ResearchWorker` / `ResearchVerifier`
(Codex CLI) or test doubles. The request returns 202 immediately. The UI
polls `GET /api/problems/{id}` every 2 s while `status == RUNNING`.

No job scheduler, no queue, no cancellation. A thread that outlives the
Codex container timeout (600 s default in `IsolatedCodexInvoker`) finishes on its own;
that is the only timeout story in V1.

Codex isolation (Slice 3 freeze amendment, final): **a cwd is not a
security boundary** — an earlier draft relied on an empty execution
workdir, which constrains context but not read access. Production workers
and verifiers therefore run `codex exec` inside one-shot Docker containers
(`IsolatedCodexInvoker`, image `noespire-codex-isolated:local`, built from
`docker/codex-isolated/Dockerfile`), not as host `CodexExec` processes.

- **Boundary:** the container's filesystem namespace. The ONLY read-write
  mount is a fresh empty host temp dir per invocation at `/work`;
  `~/.codex/auth.json` (mandatory) and `~/.codex/config.toml` (when
  present) are mounted read-only — nothing else from the host is visible:
  no `workspaces/`, no other problems' facts/attempts, no repository
  source, no home directory. Worker and verifier invocations get separate
  temp dirs, so they cannot share files; every invocation is a fresh
  ephemeral `codex exec --ephemeral` process, so no conversational context
  is reused. The temp dir is deleted on every exit path (success, nonzero
  rc, timeout — the container is `docker rm -f`'d — and parse error).
- **Inside the container** codex runs with `--sandbox danger-full-access`,
  deliberately: codex's own bubblewrap sandbox cannot create namespaces
  inside Docker (`bwrap: No permissions to create a new namespace`), which
  would break all shell tool execution. The container alone is the read
  boundary; codex's sandbox flag is not relied upon.
- **Fail-closed:** any missing prerequisite (docker executable, daemon,
  image, `auth.json`) raises `IsolationUnavailableError` at invoker
  construction, inside `_run`'s try → `ATTEMPT_FINISHED` with
  `outcome_stage: RUNTIME_ERROR`, `attempt_id: null`, claim released. There
  is NO fallback to host execution of any kind.
- **Evidence (sentinel escape experiment, this machine):** with only an
  empty dir mounted, a container-side probe attempting a relative parent
  escape (`cat /work/../secret_problem/DO_NOT_READ.txt`), absolute-path
  guesses, and a filesystem-wide `find` for the sentinel all fail
  mechanically (no such file / empty result), and a real adversarially
  prompted `codex exec` session confirmed the same through the agent path —
  the sentinel never appeared in any output while the model call itself
  succeeded (codex-cli 0.151.0).
- **Auth boundary (recorded, accepted):** the agent process inside the
  container can read its own `auth.json` — the Codex CLI architecture
  requires the credential in-container to authenticate. Only that exact
  file (plus `config.toml`) is exposed; no other host secrets are mounted.
- Integration tests (`tests/test_codex_isolation.py`) run the sentinel and
  workspace-inaccessibility probes against real containers whenever the
  daemon and image are present (skip otherwise); an opt-in real-Codex smoke
  (`NOESPIRE_RUN_ISOLATION_SMOKE=1`) covers live model invocation.

### 7.2 Execution log (application-owned evidence)

The wrapper injects its own worker/verifier adapters around the real agents
and appends JSON lines to `_execution_log.jsonl`. Four event kinds:

- `WORKER_INVOKED` — `{"execution_id", "problem_id", "attempt_id", "ts"}`,
  appended by the wrapper's worker adapter **before** it calls the real
  worker. The attempt file already exists at this point (core
  `_start_attempt` precedes `execute_obligation`), so `attempt_id` resolves
  by the same snapshot correlation. Together with `VERIFIER_INVOKED` this
  is the **per-attempt provenance** the log-completion gate requires: both
  events are wrapper-only evidence that the named attempt provably passed
  through the V1 wrapper.- `VERIFIER_INVOKED` — `{"execution_id", "problem_id", "attempt_id", "ts"}`,
  appended by the wrapper's verifier adapter **before** it calls the real
  verifier. If the process dies after the verifier returned but before the
  finish record, recovery still knows the fresh verifier was actually called.
  (`attempt_id` is derived at invocation time as the new attempt relative to
  the attempt set snapshotted when the execution started.)
- `ATTEMPT_FINISHED` — `{"execution_id", "problem_id", "attempt_id",
  "started_at", "finished_at", "outcome_stage": "PASS | CONTRACT_GUARD |
  FRESH_VERIFIER_REJECT | RUNTIME_ERROR", "verifier_called": bool}`, written
  when `solve_problem_once` returns or raises. `attempt_id` comes from
  `ProblemResult` (or the attempts dir on the exception path).
- `RECOVERED_DISCHARGED` / `RECOVERED_INTERRUPTED` — appended by startup
  recovery (§7.3); **each carries the `attempt_id` of the specific attempt
  it recovers** (plus `verifier_called` where known). The read model uses
  them to interpret residual `RUNNING` attempt files, and the binding is
  per-attempt: a recovery event suppresses live-RUNNING only for the
  attempt it names, never for later attempts of the same problem. Old
  attempt JSON is never rewritten.

`execution_id` is application-internal (log correlation only), never exposed
to the frontend; V1 runs at most one execution per problem, so correlation
by `problem_id` is unambiguous.

Log integrity rules (Slice 3 clarification): appends hold a per-workspace
lock so the background thread and recovery never interleave a line; readers
tolerate ONLY an unparseable **final** line (crash mid-append) and raise on
any corrupt non-final line; appenders first truncate a torn unterminated
final line so the invariant "at most the final line may be torn" survives
across a crash.

Recovery events bind `execution_id` **per attempt** (amended at Slice 3
freeze): when recovering attempt X, an orphan `VERIFIER_INVOKED` is one that
names X's `attempt_id` and whose execution has no `ATTEMPT_FINISHED`;
exactly one such event → reuse its `execution_id` and
`verifier_called: true`; otherwise a fresh `recovery-<uuid>` id and
`verifier_called: false`. Invocations belonging to earlier, already
recovered attempts name other attempt_ids and never pollute the binding.
Never a guess.

This log is the application layer's own instrumentation — it does not
modify, and is not read by, the research core. It also gives the UI honest
timestamps/durations (resolving the open question O2 from the interview
without touching core evidence).

### 7.3 Crash-consistency recovery

The core's PASS path is **not transactional**: the Fact is written by
`graph.add_fact` *before* `registry.resolve` discharges the obligation
(`obligation_execution.py:65-83`). A crash between them leaves a fully
verified Fact on disk with the obligation still RUNNING. Startup recovery
therefore inspects before resetting — never a mechanical RUNNING→OPEN.

On server start, for each indexed problem whose registry obligation is
`RUNNING` and for which no live task exists:

1. Read the latest attempt JSON. If `verifier_artifact.accepted == true`,
   reconstruct the content-addressed fact id from `candidate_artifact` (the
   `Fact.create` hash inputs are problem_id, statement, proof, and sorted
   predecessors; `author` is not identity-bearing). If `graph.get_fact`
   finds that fact → the crash happened between add_fact and resolve: call
   the public `registry.resolve(obligation_id, fact_id, graph)` — it
   re-checks `fact.statement == obligation.goal` — and append
   `RECOVERED_DISCHARGED`.
2. Otherwise → transition RUNNING→OPEN (a legal transition in
   `ObligationRegistry.transition`) and append `RECOVERED_INTERRUPTED`,
   including `verifier_called: true` when a `VERIFIER_INVOKED` event exists
   for that execution.

**Residual RUNNING attempts (Slice 3 freeze amendment).** Core `_start_attempt`
writes the attempt file at verdict `RUNNING` *before* `execute_obligation`
performs the OPEN→RUNNING transition (`problem.py:107` precedes
`obligation_execution.py:44`). A crash in that window leaves obligation
OPEN + attempt RUNNING + no live execution, which the RUNNING-obligation
pass above never sees. Startup recovery therefore runs a **residual pass**
(after the RUNNING-obligation pass, before log completion) over every
attempt of every indexed problem with no live execution: any attempt at
verdict `RUNNING` that no `RECOVERED_INTERRUPTED`/`RECOVERED_DISCHARGED`
event already names gets a `RECOVERED_INTERRUPTED` bound to its attempt_id
(orphan binding as in §7.2) with **no registry transition** — obligation
state belongs to the first pass alone. The pass is idempotent via the
event marker, and never touches an attempt belonging to a live execution.

Read-model mapping: an attempt file left at `verdict: "RUNNING"` is
reported with `failure_class: "interrupted"` **only when a
`RECOVERED_INTERRUPTED` event names that attempt_id** — a later attempt of
the same problem at `RUNNING` is unaffected by earlier recovery history.
The file itself is never rewritten. A problem recovered via
`RECOVERED_DISCHARGED` reads as ordinary SOLVED — the attempt JSON already
shows `verdict: "PASS"`, because the evidence wrapper persists the verifier
verdict before the fact write (`problem.py:85-90`), so no reinterpretation
is needed.

**Log completion (Slice 3 freeze amendment).** The RUNNING-obligation
recovery above does not close the *late* crash window: if the verifier
already returned, the core already reset the obligation to OPEN and wrote
the attempt verdict (FAIL/ERROR/PASS), but the process died before the
wrapper appended `ATTEMPT_FINISHED` — startup recovery skips the problem
because no obligation is RUNNING, and the read model would find a FAIL
attempt with no finish record and no way to classify it. Startup recovery
therefore runs a **completion pass after the residual-RUNNING pass**, over
every attempt of every indexed problem:

- For each attempt whose verdict is `FAIL`, `ERROR`, or `PASS` and for which
  **no `ATTEMPT_FINISHED` event names its attempt_id**, append a completion
  record: `ATTEMPT_FINISHED` with `recovered: true`,
  `started_at: null` / `finished_at: null` (timestamps are never
  fabricated), and `outcome_stage` derived from observation only:
  `PASS` verdict → `PASS`; `ERROR` verdict → `RUNTIME_ERROR`;
  `FAIL` + a `VERIFIER_INVOKED` naming the attempt →
  `FRESH_VERIFIER_REJECT`; `FAIL` with no such invocation →
  `CONTRACT_GUARD`.
- Attempts at verdict `RUNNING` are excluded — they belong to the
  interrupted paths above.
- **Honesty gate — per-attempt provenance (amended at Slice 3 freeze):** an
  attempt is completed **only when a `WORKER_INVOKED` or `VERIFIER_INVOKED`
  event names its attempt_id**. Both are wrapper-only evidence, so a named
  attempt provably passed through the V1 wrapper and "FAIL + no
  `VERIFIER_INVOKED` naming it" genuinely means the contract guard fired.
  An attempt no event names — pre-V1 or hand-seeded evidence, or a core
  failure before the worker call — is never classified: its `failure_class`
  stays `null`. A problem-level gate ("the problem has any log events") is
  explicitly rejected: it would retroactively classify pre-V1 attempts once
  the problem later runs one V1 execution, which is classification without
  evidence.
- Idempotence follows from the finish-record existence check: a second
  startup finds every completed attempt already named by an
  `ATTEMPT_FINISHED` and appends nothing.
- Ordering matters: the RUNNING-obligation pass runs first (so a window-E
  recovery resolves before any finish record is written), the
  residual-RUNNING pass second (so verdict-RUNNING attempts are marked
  interrupted before the completion pass would skip them anyway), and the
  completion pass last.

### 7.4 Exception mapping

`solve_problem_once` already resets RUNNING→OPEN and marks the attempt
`ERROR` on exception. The wrapper catches anything that escapes, appends
`RUNTIME_ERROR` to the execution log, and clears the task table entry. The
read model then shows `status: OPEN` with an ERROR attempt.

## 8. Failure Semantics

### 8.1 The gap (confirmed against source)

Contract-guard failures and fresh-verifier rejections both persist as
`verdict: FAIL` + `verifier_artifact.accepted: false`
(`obligation_execution.py:93-106` writes a synthetic `VerificationResult`;
`problem.py:134-141` persists it as `verifier_artifact`). The persisted
schema cannot distinguish origin.

### 8.2 Resolution — application-layer outcome record (chosen)

The execution wrapper (§7.2) observes whether its injected verifier adapter
was invoked during the attempt and records `outcome_stage`:

| Condition observed by wrapper | `outcome_stage` | read-model `failure_class` |
|---|---|---|
| result SOLVED | `PASS` | `null` |
| OPEN, verifier never called | `CONTRACT_GUARD` | `contract` |
| OPEN, verifier called, accepted=false | `FRESH_VERIFIER_REJECT` | `rejection` |
| exception | `RUNTIME_ERROR` | `runtime` |
| (recovery) crash between add_fact and resolve | `RECOVERED_DISCHARGED` | — (problem reads as SOLVED) |
| (recovery) other stale RUNNING | `RECOVERED_INTERRUPTED` | `interrupted` |

Because `VERIFIER_INVOKED` is appended *before* the real verifier call
(§7.2), an `interrupted` attempt can still carry `verifier_called: true` —
the UI may then say "the fresh verifier was called; its verdict was lost to
the crash" instead of implying verification never happened.

Rejected alternative: adding `failure_source` to the core attempt schema
(`src/research/problem.py`). Rejected because the core's evidence contract
is experiment-grade and frozen by tests; the wrapper's observation is
strictly more honest (it watches the actual call) and costs zero core churn.
If the evidence schema later gains a first-class origin field, the read model
should prefer it and the log becomes redundant — a pure deletion.

The prototype-only `failureSource` field does not survive into production;
`failure_class` replaces it, sourced as above.

### 8.3 Display contract

Three failure classes keep the prototype's distinct labels/glyphs/next-action
copy (`Contract failure` / `Verification rejection` / `Runtime error`, plus
`Interrupted` using the runtime styling). Never a generic "Verifier Failed".

### 8.4 Research-core touchpoints

None. This spec requires no edits to `src/research/` and no test changes
there. The RUNNING→OPEN recovery transition (§7.3) uses the public registry
interface.

## 9. Frontend Information Architecture

Routes: `/` (Home) and `/problems/:problemId` (Workspace). Nothing else.

**Home** — problem rows: statement snippet, status badge, attempt count,
`Derived from …` link, last activity; archived hidden behind a filter;
`+ New Problem` (single statement field).

**Workspace**:

- Header: statement (serif), status badge, `LLM-verified` badge slot (shown
  only when SOLVED), actions per state — OPEN → `Retry` + `Revise & Fork`;
  RUNNING → Retry disabled ("already running"); SOLVED → `Revise & Fork`;
  ⓘ opens the Inspector; `Derived from …` link when applicable.
- Tabs: `Proof | Attempts`. Default tab: SOLVED→Proof, OPEN/RUNNING→Attempts.
  No Graph tab in V1 (the additive slot is documented, not rendered).
- Proof tab: target proof document (KaTeX, serif), mathematical clickable
  Fact references ("by Lemma 1" — never raw ids), supporting-closure list
  below the document (multi-node closures only; single-fact closures render
  as a one-line note). OPEN problems show the honest empty state.
- Attempts tab: latest attempt expanded (candidate proof in the unverified
  register — dashed/amber container, `Unverified` banner), failure panel with
  class-specific label/glyph/suggestion, earlier attempts as collapsed
  timeline entries. RUNNING shows the phase line (`Generating candidate…` /
  `Checking candidate…`, marked "live · phase inferred") with session-scoped
  elapsed time.
- Inspector: right overlay drawer (scrim, ✕, Esc). Contents: ids
  (problem/obligation/attempt/fact), predecessors, route_id, candidate &
  verifier artifacts, lineage, raw JSON of the focused object.

Visual system: the prototype's token set carries over verbatim (light only,
HSL custom properties, monochrome accent, blue-cyan for LLM-verified, amber
OPEN, red ERROR, serif 16–18px body, 11–13px chrome).

```text
src/

├── types.ts        # mirrors the REST contract (§5/§6), nothing else
├── screens/
```

## 11. Test Plan

Application (pytest, scripted worker/verifier doubles — the same pattern as
`tests/test_obligation.py`; no Codex calls):

1. create problem → listed, OPEN, no obligation yet;
2. list reflects archive toggle and lineage;
3. start attempt → RUNNING while double is blocked, then:
   PASS → SOLVED + target fact + closure; FAIL(verifier) → OPEN +
   `rejection`; FAIL(guard) → OPEN + `contract` (double returns mismatched
   statement); exception → OPEN + `runtime`;
4. second `POST …/attempts` during a live run → 409;
5. solved reload → no worker/verifier re-invocation (counter double);
6. fork → new id, `derived_from` set, old problem untouched;
7. read model: field presence/nullability per state; `interrupted` mapping
   after simulated restart (RUNNING obligation restored to OPEN);
8. execution log written with correct `outcome_stage` per case.

Frontend (Vitest + Testing Library, mocked `api/`):

1. state → default tab (SOLVED/OPEN/RUNNING);
2. failure-class rendering: three classes get three distinct labels;
3. Retry disabled + 409 handling while RUNNING;
4. `LLM-verified` badge present on SOLVED proof, absent elsewhere; candidate
   proofs render in the unverified register;
5. Inspector opens from header and from an attempt, shows raw JSON, closes

## 13. Implementation Order

Five slices, each independently testable and demo-able:

- **Slice 1 — Read spine.** `problem_index`, `workspace_read_model`,
  `GET /api/problems`, `GET /api/problems/{id}`. Seed one fixture-like
  workspace on disk by hand. Proves the read seam end to end.
- **Slice 2 — Create + Home.** `POST /api/problems`, Home screen, minimal
  Workspace shell (header + tabs + Inspector, static states).
- **Slice 3 — Execution.** `execution` wrapper, execution log,
  `POST …/attempts` + 409, polling, RUNNING indicator, restart recovery.
- **Slice 4 — Workspace states.** Proof tab (document, closure, references),
  Attempts tab (timeline, failure panels), full state matrix.
- **Slice 5 — Mutations.** Fork, Archive, lineage display, Home polish.

Each slice lands behind the REST contract; the frontend never blocks on a
later application slice (mock `api/` first, swap in the real server).

## Freeze Rulings (decided at spec freeze)

1. **Startup recovery may mutate core state — but never mechanically, and
   only through public interfaces** (§7.3). A crash between `add_fact` and
   `registry.resolve` is recovered to DISCHARGED via the public
   `registry.resolve(...)`; all other stale RUNNING obligations return to
   OPEN. Recovery is recorded in the application-owned execution log
   (`RECOVERED_DISCHARGED` / `RECOVERED_INTERRUPTED`); core attempt JSON is
   never rewritten.
2. **`POST …/attempts` on a SOLVED problem returns 409 `already_solved`**
   (§6). 202 means "accepted for execution"; a discharged obligation
   executes no worker/verifier, so a silent no-op would lie about what
   happened.
3. **202 responses carry no core attempt id** (§6). `_start_attempt`
   sequencing in `problem.py` stays untouched; one-execution-per-problem
   plus read-model polling is sufficient. An internal `execution_id` for log
   correlation is allowed but never exposed to the frontend.

Plus the instrumentation rule: `VERIFIER_INVOKED` is appended **before** the
real verifier call, so a crash between verifier return and finish record
still preserves that the fresh verifier ran (§7.2, §8.2).
